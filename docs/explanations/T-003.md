# T-003 - Prove the local gate blocks bad pushes

## What it is
A **git hook** is a script git runs automatically at a fixed moment. The one used here runs *before a push*. If the script exits with a non-zero code, git abandons the push and the remote never receives anything. That is a **blocking gate**, not a warning: it is not advisory, it does not "remind" you, it stops the transfer.

Analogy: a turnstile that only opens when your ticket scans. A sign saying "please buy a ticket" is a reminder; the turnstile is the gate.

## What I built here
Nothing in `src/` changed. This task is a **proof exercise**: deliberately do six bad things, try to push each one to a throwaway remote, and record that git refused every time. Then undo everything.

The six bad actions, each mapped to the rule it should trip:

| # | Bad action | Expected gate |
|---|---|---|
| a | a failing test | pytest inside `make verify` |
| b | a lint error | ruff inside `make verify` |
| c | a fake AWS key in a text file | guard `check_secrets` |
| d | a task left `IN_PROGRESS` | guard `start-to-finish` |
| e | a task marked `DONE` with no explanation file | guard `explanation-missing` |
| f | a dependency not in `docs/ALLOWED_DEPS.txt` | guard `dependency-not-allowed` |

Why DevReview needs this: the whole project depends on the claim "the gate stops bad work". Until someone demonstrates the stop with real output, that claim is a hope. This is also the task that proves the agent cannot quietly push around the rules.

## How it works
1. `git init --bare` creates an empty repository with no working tree — a valid push target that cannot affect GitHub. The task's `/tmp/devreview-remote.git` is a Unix path, so on this Windows machine the sandbox lived at `%TEMP%\devreview-remote.git` instead.
2. `git remote add sandbox <path>` registers it under a name, next to `origin`.
3. `git checkout -b experiment/t-003` creates a throwaway branch so no real work is touched.
4. Each bad action is applied, then `git push sandbox HEAD` is attempted. Git runs `.git/hooks/pre-push`, which runs `make verify`; when that fails, git prints `error: failed to push some refs`.
5. Afterwards every experiment is reverted, the remote is removed, the bare repo is deleted, and the throwaway branch is deleted.

One detail that matters: the pre-push hook evaluates the **working tree**, not just the committed snapshot. So for (b) and (c) the bad file never had to be committed — an uncommitted bad file is enough to block the push. That is stricter than the task asked for.

## What could go wrong
- **Local hooks can be skipped.** `git push --no-verify` bypasses `pre-push` entirely. This is why a local gate is not enough on its own and why branch protection plus CI (T-004, T-005) exist. The local gate stops accidents and honest mistakes; the server-side gate stops everything else. See `docs/GUARDRAILS.md`.
- **A hook needs its tools on PATH.** With the venv inactive the hook fails with `Executable 'ruff' not found` — the push is still blocked, but for a confusing reason.
- **`git reset --hard` during an experiment** silently discarded an unrelated working-tree edit (`docs/PROGRESS.md`) in this session; it was re-applied. Lesson: check `git status` before any hard reset.
- **Forgetting to revert** would leave a fake secret or an unapproved dependency in the tree. Every experiment was reverted and `git status` re-checked; only the legitimate T-003 progress entry remains.
- **Pushing the experiment to `origin`** would have published junk. The sandbox remote is a local bare repo; nothing reached GitHub.
