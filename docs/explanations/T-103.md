# T-103 - Find bug-introducing commits (simplified SZZ)

## What it is
SZZ (named after its creators Śliwerski, Zimmermann, and Zeller) is an algorithm that works backwards from a bug fix to find the exact commit that originally introduced the bug. Think of it like a detective: when a plumber fixes a broken pipe, you look at who installed or last touched that specific section of pipe.

## What I built here
- `BuggyLocation`: a structured record `{introducing_sha, file, start_line, end_line}` pointing to the exact commit and line numbers where buggy code was introduced.
- `find_introducing_commits(repo_path, fix_sha) -> list[BuggyLocation]`: implements the simplified SZZ algorithm.
- `tests/test_szz.py`: unit tests verifying detection with throwaway Git repositories, including skipping whitespace-only commits via `git blame -w`.

DevReview needs this because to create our ground truth dataset (the answer key for evaluating AI reviewers), we need to know not just that a bug existed, but which historical commit introduced it and on which lines.

## How it works
1. **Find parent commit:** Determine the parent commit `P` of fix commit `F` (`F^`).
2. **Find modified/deleted lines:** Run `git diff -U0 F^ F` to extract line ranges in parent `P` that were changed or removed by the fix. If a fix only added new lines (e.g. adding error handling), no lines were deleted and no introducing commit is flagged.
3. **Trace lines back in time:** For each deleted range, run `git blame --porcelain -w -L start,end P -- file`.
   - The `-w` flag tells git to ignore whitespace-only changes, skipping formatting commits that didn't change logic.
   - The porcelain header format is `<sha> <orig_line> <final_line>`. The second number (`orig_line`) tells us the exact line number inside the introducing commit where that line lived.
4. **Group contiguous lines:** Group consecutive blamed lines sharing the same introducing SHA and file into `BuggyLocation` objects.

## What could go wrong
- **Refactoring noise:** SZZ blames the commit that last touched the deleted lines. If a developer refactored or renamed variables without introducing a bug, SZZ might blame the refactoring commit instead of the original author of the bug.
- **Root or merge commits:** Calling SZZ on a root commit (no parent) or a multi-parent merge commit will fail unless parents are specified. (Per specification, fix commits are non-merge commits).
- **Deleted files:** If the fix commit completely deletes a file, `git blame` runs against `F^` on the deleted file, which is valid in Git history.

## Check yourself
1. When a bug fix commit modifies line 15 of `utils.py`, why does SZZ run `git blame` on the parent commit (`fix^`) instead of the fix commit itself?
   - **Answer:** If we blamed the fix commit, Git would show the developer who actually solved or fixed the bug, rather than who introduced it. Blaming `fix^` inspects the code before the fix was applied.
2. If someone ran a code formatter (Prettier / Black) that changed indentation on the buggy line before the fix commit was made, why doesn't SZZ blame the formatter commit?
   - **Answer:** The `-w` flag tells git to ignore/exclude whitespace differences (spaces, tabs, newlines), so Git skips formatting commits and finds the commit that actually wrote the code.
