# T-104 - Build the golden dataset file

## What it is
A "golden dataset" is an answer key for testing an AI reviewer: a curated file of real code changes where we know whether each change was buggy or clean. **JSONL** (JSON Lines) is a standard format where every line in the file is a separate, self-contained JSON object.

## What I built here
- `Case` schema and `docs/schemas/case.md`: standardized structure `{id, repo, commit_sha, parent_sha, label, fix_sha, buggy_locations, diff}`.
- `validate_case()`: strict schema validator on write (checks types, SHA formats, label consistency, and diff length without external dependencies).
- `build_dataset()`: scans a git repo, identifies buggy commits via SZZ, selects clean commits (commits older than cutoff that touch code files and have no later fix), skips diffs exceeding the size cap, and writes valid JSONL lines.
- `devreview dataset build`: CLI command with `--out`, `--max-diff-lines`, and `--min-age-days`.
- `tests/test_dataset_builder.py`: test suite confirming round-trip build & read, strict schema validation, diff size filtering, and CLI output.

## How it works
1. **Find fixes & bugs:** Calls `find_fix_commits()` and `find_introducing_commits()` to map bug-introducing commits and their line locations.
2. **Collect candidate commits:** Iterates through all single-parent non-merge commits in git history.
3. **Classify cases:**
   - If a commit is an introducing commit, it is labeled `"buggy"`, linked to the `fix_sha`, and given the `buggy_locations`.
   - If a commit is not an introducing commit, is at least `min_age_days` (default 90) older than HEAD, and touches source code files, it is labeled `"clean"`.
4. **Diff size cap:** Computes `git diff -U3 parent commit`. If the diff exceeds `max_diff_lines` (default 400), it is skipped and counted.
5. **Validate & write:** Runs `validate_case()` before writing each line as JSON to the output `.jsonl` file. Prints the total counts of buggy, clean, and skipped cases.

## What could go wrong
- **Why the diff size cap exists:** Large diffs (e.g. 5,000-line library vendorings or dependency lockfile bumps) consume tens of thousands of tokens, driving up LLM review costs and exceeding model context limits. Capping diffs at 400 lines prevents expensive out-of-context backtests.
- **Why the 90-day clean cutoff exists:** A commit made yesterday has no known fix yet, but might contain an undetected bug. Requiring clean cases to be at least 90 days old gives real human users time to find and report bugs, reducing the chance that an unfixed bug is mislabeled as "clean".

## Check yourself
1. Why is JSONL (one JSON object per line) better for machine learning datasets than putting one giant `[ {...}, {...} ]` JSON array in a single file?
   - **Answer:** JSONL acts as independent single-line data objects rather than a giant multiple-object array. This allows reading and streaming line-by-line with minimal memory usage, easy appending, and efficient processing without memory crashes.
2. If an AI reviewer flags a bug in a commit that our dataset labeled "clean", does that guarantee the AI was wrong? Why or why not?
   - **Answer:** No, it is not guaranteed to be 100% bug-free. "Clean" only means no later commit fixed a bug in it; a real bug might still be present that humans missed or never fixed. The AI might have caught a real, unfixed bug.
