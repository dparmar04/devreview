# T-105 - Build a dataset from a real public repo

## What it is
Testing our dataset builder pipeline on a real-world, battle-tested open-source repository ([`psf/requests`](https://github.com/psf/requests)) rather than simulated toy fixtures. This produces our actual ground truth dataset for evaluating AI code reviewers on real production code.

## What I built here
- Generated `datasets/requests.jsonl` from `psf/requests` containing 2,129 real cases.
- Generated `datasets/README.md` documenting repository metadata (URL, commit hash, Apache 2.0 license) and case distributions.
- Handled edge cases discovered on real repository history: robust UTF-8 decoding with character replacement for non-ASCII commit metadata, and graceful error recovery for unusual diff boundaries.

## How it works
1. **Target Repository:** Cloned `https://github.com/psf/requests.git` (commit `3c7baaa05ab4aa49cc819ce3a819d260de19c157`).
2. **Execute Builder:** Ran `devreview dataset build <path> --out datasets/requests.jsonl --max-diff-lines 400`.
3. **SZZ Processing:** Traced 538 buggy cases back to their introducing commits and lines.
4. **Clean Baseline:** Gathered 1,591 clean commits older than the 90-day cutoff that touched Python code files and were never modified by a later fix.
5. **Capped Diffs:** Skipped 92 commits whose diff exceeded 400 lines (e.g. large vendored packages or bulk dependency bumps).

## What could go wrong
- **What the numbers say about how rare real bugs are:**
  In `psf/requests`, out of 2,129 total evaluated commits, only **25.3%** were bug-introducing. That means roughly **3 out of every 4 code changes are completely clean**. In enterprise software, real bugs are often even rarer (typically 5% to 15% of changes).
  If an AI code reviewer flags issues on 50% of PRs, it is likely flooding developers with false alarms. This skew is why precision and false-alarm metrics are so critical in AI evaluation.

## Check yourself
1. In `psf/requests`, ~75% of changes are clean and ~25% are buggy. If an AI reviewer comments on 80% of all pull requests, what does that tell you about its behavior?
   - **Answer:** It has a high false-positive rate and is spamming developers with unnecessary comments on clean code, causing developer fatigue where there was nothing to comment on.
2. Why is building the dataset from a real public repository with 1,000+ commits more trustworthy than testing only on artificial fixture repos?
   - **Answer:** Real repositories contain authentic commit messages, diverse developer writing styles, real human bugs, and real fixes, providing an unbiased ground truth test set rather than an overfitted artificial benchmark.
