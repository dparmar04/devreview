# T-002 - Make `make verify` green

## What it is
A **linter** reads code without running it and complains about style and likely mistakes (unused imports, wrong import order, shadowed names). A **test runner** executes your tests. A **security scanner** looks for risky patterns in your code; a **dependency audit** looks up your installed libraries in a public list of known vulnerabilities. A **git hook** is a script git runs automatically before an action; if the script exits non-zero, git cancels the action.

Plain analogy: `make verify` is the pre-flight checklist. Ruff checks the paperwork, pytest starts the engine, bandit and pip-audit check the fuel lines, and guard reads the pilot's logbook.

## What I built here
Nothing new in `src/` — this task is about making the existing safety net *work* on this machine.

- Ran `make setup`: upgraded pip, re-installed the package in editable mode with the `dev` extras, and installed the git hooks.
- Confirmed the hooks are on disk: `.git/hooks/pre-commit` and `.git/hooks/pre-push`.
- Ran `make verify`. Four of five stages pass; the fifth (guard) fails only because T-002 is still `IN_PROGRESS`, which is guard doing its job.
- Found one real problem: the installed **pre-push hook calls `make verify`**, and this machine has no `make` binary, so every future `git push` would be blocked with `Executable 'make' not found`. That is a machine/tooling decision for the human, recorded in `docs/QUESTIONS.md`.

Why DevReview needs this: from now on, "it works" must mean "all five gates pass on a clean run". Without that, an AI agent can push broken or unsafe code and nobody notices until much later.

## How it works
1. `make setup` = `pip install --upgrade pip`, then `pip install -e ".[dev]"`, then `pre-commit install`.
2. `pre-commit install` writes small scripts into `.git/hooks/`. Git runs them by filename: `pre-commit` before a commit, `pre-push` before a push.
3. The `pre-commit` hook runs ruff lint, ruff format check, and a fast secret scan. The `pre-push` hook runs the whole `make verify`.
4. `make verify` runs `lint`, `test`, `security`, `guard` in that order and stops at the first failure.
5. `scripts/guard.py` reads `docs/PROGRESS.md` and `docs/explanations/`. It refuses to let a push through while a task is `IN_PROGRESS`, or when a `DONE` task has no explanation file.

To see the hooks themselves:

```

```

Expected: three hooks, `Passed`, including `secret scan (fast)`.

## What could go wrong
- **Pushing without the venv active**: the hook runs `make verify`, whose recipes call bare `ruff`, `pytest`, `bandit`, `pip-audit`. Outside the venv they are not on PATH, so the push is blocked with `Executable ... not found` or `make (e=2)`. You would notice the push refused with those lines. Fix: activate the venv first. `.pre-commit-config.yaml` states this requirement in its header comment.
- **`make` missing entirely on this machine**: the pre-push hook fails with `Executable 'make' not found` even with the venv active. Every push is blocked. Resolved on 2026-11-07 by human decision (b): `mingw32-make.exe` was copied to `make.exe` in the same folder, so the bare name `make` now resolves. See `docs/QUESTIONS.md` Q2.
- **pip-audit needs internet**: with no connection it errors instead of reporting. You would see a network error in the `security` stage.
- **`pip-audit` skip line**: `devreview Dependency not found on PyPI and could not be audited` is expected — it is this local package, not published.
- **Guard failure messages are literal**: they name the task and the rule. Do not silence them; fix the state in `PROGRESS.md` or add the missing explanation.
