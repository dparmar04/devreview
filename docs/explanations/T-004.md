# T-004 - CI runs on pull requests

## What it is
**CI** stands for continuous integration: a robot that takes your code, puts it on a *brand new machine* that has none of your setup, installs the project from scratch, and runs every check again. It runs on GitHub's servers, not yours.

The point is not "tests run twice". The point is **the second machine knows nothing about your machine**. Your laptop has a venv with just the right packages, a PATH with the right tools, a `.env` file, and your memory of what you changed. GitHub's runner has none of that. If the code only works because of something on your laptop, CI is where that shows up.

Analogy: a recipe you cooked successfully in your own kitchen proves nothing about whether the recipe is written down correctly. Someone else cooking it in an empty kitchen is the real test.

The word **gate** matters here too: CI is not a report you read. With branch protection (T-005) a red CI run *refuses the merge*. This task proves the red is real.

The test itself:

```python
assert os.environ.get("CI") != "true", "deliberate CI-only failure for T-004"
```

Why "CI-only" and not just "failing"? Because a test that fails locally could never be pushed at all: the pre-push hook runs `make verify`, pytest fails, git refuses. The only way past that would be `--no-verify`, which AGENTS.md forbids. A CI-only failure is honest — the local gate still passes truthfully, and the server gate is what turns red.

Why this project needs it: the whole guardrail story claims "bad work cannot reach `main`". T-003 proved the *local* half. This task proves the *server* half actually executes and actually fails.

### The design conflict, and how it was resolved
T-004 needs a PR whose CI is red. But guard blocks any push while a task is `IN_PROGRESS` (`[start-to-finish]`). A red CI run needs a push; a push is forbidden mid-task. The two rules collide.

Chosen resolution (option **a**, approved by the human): keep T-004 as `TODO` in the ledger for the two experiment commits, then flip straight to `DONE` in the final commit. No `--no-verify`, no hook skipped, no rule bent — the ledger simply never says `IN_PROGRESS` for this one task. Recorded in `docs/QUESTIONS.md`.

## How it works
1. `git push` to a branch triggers `.github/workflows/ci.yml` because the workflow listens on `pull_request` (and on pushes to `main`).
2. GitHub starts two jobs on `ubuntu-latest`, in parallel: `verify` and `secrets`.
3. `verify` runs: checkout (full history) → setup Python 3.12 → `pip install -e ".[dev]"` → `make verify` → `python scripts/guard.py --commits origin/main`.
4. `make verify` is the same sequence used locally: ruff lint, ruff format check, pytest, pip-audit, guard. It stops at the first failure, exactly like locally.
5. The `secrets` job runs `gitleaks/gitleaks-action`, a separate secret scanner that looks at the diff, using the repo's own `GITHUB_TOKEN`.
6. Each job reports a **check run** back to the PR. Green = success, red = failure. Branch protection reads those check runs.

A detail worth knowing: `make verify` runs the *guard*, which reads `docs/PROGRESS.md` from the branch. So a task left `IN_PROGRESS` would also fail in CI, not only locally.

## What could go wrong
- **A local pass is not a CI pass.** Different OS (Linux vs Windows), different Python patch version, no venv, no `make` alias. The first CI run of a new project usually fails for setup reasons, not logic reasons.
- **The two environments can drift silently.** CI pins `python-version: "3.12"` while local may be 3.13, and CI installs from `pyproject.toml` with `.[dev]`, so a package that is only installed manually on the laptop will be missing.
- **A red check is not a blocked merge — yet.** GitHub will happily let you merge a red PR unless branch protection requires the checks. That is T-005, and it is why T-004 alone does not finish the story.
- **Deprecated action runtimes.** The red run emitted: `Node.js 20 is deprecated. The following actions target Node.js 20 but are being forced to run on Node.js 24: actions/checkout@v4, actions/setup-python@v5.` It works today, by force-mapping, but that mapping is temporary.
- **A test that behaves differently on CI is a trap if left in.** `test_ci_proof.py` was deleted in the very next commit; leaving it would make every PR red forever.
- **Secrets job false confidence.** `secrets` passed on both commits — correct, because the fake key experiment (T-003) never went to GitHub. A green `secrets` job only means "no known secret pattern in this diff", not "no secrets in the repo".
